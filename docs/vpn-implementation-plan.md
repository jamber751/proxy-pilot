# VPN: план реализации

Дата: 7 сентября 2026. База: ProxyPilot 1.5.1, commit `0518754`.

Статус: реализация начата 7 сентября после согласования макета. Готовы слой конфигурации с проверкой профиля и хранением, безопасная миграция старых маршрутов и привилегированный слой: межпроцессное владение службой, launchd-адаптер с подтверждённой очисткой, аутентифицированный канал с типизированными запросами, установка и удаление службы. 8 сентября пройдена системная приёмка рабочей idle-службы без движка; тот компонент был удалён. В новом прогоне комплекта с движком подтверждены установка 4, повтор 4, обновление 4 → 5 и полное удаление 5. Тестовая root-служба и движок больше не установлены. Подключение VPN и новый интерфейс не активированы: туннель не поднимался, сетевые настройки пользователя не изменены.

**Инертный прототип, живой прогон 7 сентября:** 7 из 8 сценариев подтверждены.
Окончательная очистка завершена после подтверждения владельца: Installer показал
успех, label, два файла, процесс и installation receipt отсутствуют. Оба клиента
0.0.1/0.0.2 завершаются с кодом 69 (служба недоступна). Повторных установок для
проверки Cancel не запускаем; этот сценарий остаётся неподтверждённым.
Реальный VPN не подключался, профиль не передавался тестовой службе.

## Ход реализации

Режим работы подтверждён владельцем: продолжать последовательно и автономно,
самостоятельно проверять результат и сохранять логические коммиты; не спрашивать
разрешение на каждый следующий пункт. Это не расширяет разрешение на публикацию,
настоящую системную установку или изменение сети. При необходимости новых прав
или существенного решения вне согласованного плана остановиться на этой границе.

### Согласованное дополнение: вход в VPN (13 сентября)

Поддержать три простых режима: сертификат без пароля, постоянный пароль и
одноразовый код вместо пароля. Для нового профиля владелец сообщил, что вход
проходит с кодом Google Authenticator без постоянного пароля; живое подключение
нами не проверялось. Исходный файл содержит `auth-user-pass`, но по этой директиве
нельзя определить тип пароля. Логины, ключи и коды в план/тестовые данные не переносим.

- [x] Модель и миграция: хранить только выбранный режим, логин и намерение
  сохранения постоянного пароля, без секретов. Импорт различает профили с
  `auth-user-pass` и без; тип пароля не угадывает. Старые конфигурации и ресурсы
  сохраняются, режим остаётся невыбранным. Замена содержимого профиля не может
  унаследовать данные входа даже при прежнем имени файла и прямом вызове хранилища.
- [ ] Минимальный UI: без пароля — сразу подключить; постоянный пароль — форма
  входа и необязательное сохранение; код — только запрос свежего кода. Изменение
  режима доступно внутри настроек VPN, без дополнительных элементов на главном экране.
  Для `auth-user-pass` один раз предложить «Пароль» / «Одноразовый код».
- [ ] Секреты: постоянный пароль сохраняется в Keychain только по явному выбору;
  одноразовый код не сохраняется в конфиг, Keychain, лог или отчёт. Пароль
  зашифрованного клиентского ключа — отдельный запрос, не смешивать с паролем VPN.
- [ ] Подключение: передать данные через защищённый канал текущей попытки,
  не через argv/файл настроек. Отмена/выключение инвалидируют запрос и поздний ответ.
  Просроченный/неверный код даёт повторный ввод, без автоматического перебора.
- [ ] Переподключение: новый код запрашивается только при новом требовании входа
  от сервера; старый не отправляется повторно. Если повторная авторизация не нужна,
  не прерывать соединение лишним запросом. Не путать токен сессии с сохранённым OTP.
- [ ] Приёмка: каждый из трёх режимов, миграция, отмена, неверный/просроченный код,
  повторное подключение, закрытый Keychain, отсутствие секретов в сохранениях и
  диагностике. Серверные challenge/response, SSO и пароль+код слитно не считать
  автоматически поддержанными режимом «одноразовый код вместо пароля».

Разработка независимых частей разрешена параллельно на Sol; исполнители отмечают
свои изменения и проверки в отдельных рабочих заметках. Общий план и итоговую
приёмку обновляет основной агент после проверки. Работа с настоящим VPN, системной
установкой и публикацией не расширяется самим фактом параллельной разработки.

### Прогресс на 27 сентября

Общий маршрут: **этап 1 из 7 в работе — установка и безопасные обновления**.
Слой конфигурации/импорта из этапа 2 частично готов параллельно. Полностью
закрытых этапов пока нет: количество тестов не означает готовность живого VPN.

Текущий рубеж — позднее восстановление совместного обновления приложения и
VPN-компонента. Защищённый content-addressed helper B теперь регистрируется
отдельной launchd-задачей до смены selector, поэтому падение после выбора B или
перезагрузка продолжают только вперёд, без запуска изменяемого пути из
`/Applications`. Обычный успешный путь и восстановление используют один
финализатор и удаляют терминальный журнал; uninstall снимает обе launchd-задачи.

- [x] Восстановление `replacementPending/recoverCandidate`, `selected` и
  `completed`, включая принудительное завершение сразу после atomic rename
  `release.json` и новый процесс восстановления.
- [x] Recovery-only запуск helper допускает только root readiness до удаления
  терминального журнала; пользовательские команды в этом окне закрыты.
- [x] Отдельная launchd-задача запускает только повторно проверенный helper из
  защищённого хранилища, вооружается до live-B handshake и переживает reboot.
- [x] Обычный updater учитывает recovery plist как установленный VPN-компонент
  и не начинает несогласованный Sparkle update.
- [x] Для будущего updater handoff добавлен фиксированный приватный каталог
  `ProxyPilot/Update` и отдельный resumable staging: exact A и B публикуются в
  `current` / `candidate` только после полной проверки подписей и отдельного
  подписанного разрешения перехода A→B. Пустой или полностью проверенный
  `.preparing` после падения продолжается вперёд; чужое состояние не удаляется.
- [x] Update-пакет теперь несёт предыдущий signed manifest и отдельный signed
  transition A→B, проверяет весь набор собственным production verifier до GUI и
  до системных записей. Инструмент выпуска сам строит канонический transition.
  Старый helper-only `--vpn-support-update` закрыт: он мог выбрать helper B,
  пока в `/Applications` оставалась A. До подключения executor handoff update
  завершается безопасным отказом, а не частичной установкой.
- [x] Executor handoff разделяет identities: родитель-кандидат B проверяет exact
  child A, а child A независимо проверяет parent B. Неверная identity любой
  стороны блокируется до GO и до записи журнала; 10/10 handoff-сценариев прошли.
- [x] Добавлена возобновляемая preparation-фаза без stop/select: под service→app
  lock order она связывает установленную A, package B и signed transition,
  публикует A/B slots, durable update journal и executor A. Падение после app
  staging или journal продолжает только вперёд; повтор не переписывает готовые
  объекты. 4/4 coordinator и 7/7 staging-сценариев прошли.
- [x] Fixed root update entry подключён к этой фазе и descriptor-only handoff:
  package B не меняет selector сам, а запускает protected executor A. A под одной
  service lease валидирует slots, drain-ит helper, фиксирует
  `prepared→replacementPending` и продолжает существующий full replacement,
  live-B/readiness/finalizer. Joint suite 19/19, preparation 5/5.
- [x] Проверки: launchd + joint 30/30, installer 36/36, package 10 обязательных
  из 10 (3 внешних engine-сценария пропущены), admission 10/10; Universal helper
  собран для arm64/x86_64 и прошёл strict codesign.
- [x] Новый staging: 7/7 сфокусированных сценариев; signing tool 13/13;
  package-композиция 14/14 обязательных сценариев, 3 внешних engine-сценария
  пропущены.
- [ ] Следом — root-приёмка полного package handoff на одноразовой установленной
  копии и crash/reboot границах; затем отдельной транзакцией безопасно удалить
  retained A, executor и destination-stage только после подтверждённой
  B/readiness и retirement. Обычный Sparkle updater пока намеренно ставит veto.

Текущее продолжение — связка журнала, владения службой и защищённых копий.

### Продолжение 1.5b — хранение политики и отказы при прерывании записи

Добавлен `app/vpn-helper/VPNReleaseStore.swift`: получает уже открытый доверенный
дескриптор каталога, дублирует его без наследования дочерними процессами, сверяет
владельца/0700 и отсутствие ACL. Все операции относительно этого дескриптора;
данные, marker и lock — только обычные 0600 файлы одного владельца без ссылок и
ACL. Ключ доверия передаётся из доверенного контекста, не читается из записи.
Фиксированный системный путь и его безопасное создание ещё не подключены.

Запись содержит подписанный релиз и неизменяемого владельца. При каждом чтении
подпись проверяется снова. Обновление перечитывает предыдущую политику под
межпроцессной блокировкой, сверяет ожидаемый номер и проверяет запрет отката.
Повтор того же описания не переписывает файл даже при другой допустимой подписи.
Права root/каталог root в живой системе на этом шаге не запрашивались: в тестах
хранилище проверяет UID обычного тестового процесса; в будущей службе это UID 0.

При первой инициализации marker сохраняется раньше записи. Повреждение/удаление
записи не превращается в пустое хранилище, повторный bootstrap не разрешается.
Прерванная первая установка требует отдельного авторизованного восстановления,
а не автоматического сброса. Обновление использует временный 0600 файл, fsync,
rename и fsync каталога. Ошибка после rename означает неопределённый результат
с необходимостью перечитать состояние, а не обещание «ничего не изменилось».

`tests/test_vpn_release_store.py` / `tests/vpn_release_store_checks.swift` проверяют
перезапуск отдельными процессами, сохранённый запрет отката, устаревшего писателя,
повтор/конфликт, неподходящую подпись, повреждение/удаление, блокировки, права/ACL,
ссылки/FIFO, прерывание до/после rename и прерванную первую инициализацию. Аварийные
остановки доступны только в тестовой компиляции. Проверки выявили и помогли исправить
различие отсутствующей ACL и ошибки её чтения, а также лишнюю перезапись при
повторном предъявлении того же описания с другой действительной подписью.

Это проверка аварии процесса, **не физического отключения питания**. Временные
файлы после аварии остаются в частном каталоге и не принимаются как политика;
их автоматическая очистка пока не реализована. Защита не распространяется на
root, намеренно заменившего весь каталог старым снимком. `accept` сохраняет
разрешение, не устанавливает бинарник: согласование активации службы/политики и
восстановления ещё обязательно. Рабочее приложение и пакеты не изменены.

Ранее подготовленная работа разделена на пять коммитов: слой данных/импорт,
инертный установочный прототип, проверка клиента/подписей, изоляция updater,
документация рубежей. Новый слой хранения фиксируется отдельным следующим
коммитом после регрессии. Пуш и публикация не выполняются.

Итог: все **16 новых проверок хранилища прошли**. Полный прогон — **106 тестов
за 116 секунд: 105 успешно, 1 пропущен** (opt-in установка Sparkle в одноразовое
приложение). Обе архитектуры собраны с target macOS 11; обычная компиляция без
тестовых аварийных остановок также проверена. Исполнение — только на текущем Mac.
На завершение этого прогона следующим пунктом были: безопасное создание root-owned каталога и согласованная
активация бинарника/политики с восстановлением, затем интеграция updater и
аутентифицированного транспорта. Рабочий VPN ещё не подключается.

### Продолжение 1.5b — защищённый каталог и дисковая транзакция развёртывания

`VPNDirectoryProvisioner.swift` реализует root-проверку до открытия системных

Несовместимые существующие каталоги не исправляются и не очищаются автоматически.
Возвращается дескриптор без наследования дочерними процессами. 7 тестов проходят
под обычным пользователем во временном каталоге. Положительная установка под
root, реальные ACL родителей и старые установки остаются в живой приёмке.

`VPNHelperArtifact.swift` проверяет точные байты по подписанному описанию и
реальную подпись обоих срезов arm64/x86_64. Дополнительно проверяются формат
Universal, тип исполняемого файла, соответствие CDHash своей архитектуре,
идентификатор службы, hardened runtime/hard/kill и отсутствие entitlements.
Сетевые проверки подписи отключены; нотариализация этим не подтверждается.
Используется защищённый файл и сверка inode/устройства: статическая проверка
Security API требует отсутствия недоверенной конкурентной записи в каталог.

В `VPNReleaseStore` добавлен schema 2 и отдельные методы развёртывания. Сначала
валидируется и сохраняется файл `helper-<SHA256>` с 0700, затем одной атомарной
записью выбираются и политика, и связанный с ней бинарник. Прежний файл остаётся;
сохраняется владелец. На каждом чтении выбранный бинарник проверяется повторно.
Метод обновления только политики не может разрушить эту связь; незаметной
миграции schema 1 → 2 нет. Сбой до записи выбора оставляет старую пару, сбой
после — целую новую. Повреждённые файлы/ссылки не перезаписываются автоматически;
пропажа выбранного бинарника не вызывает скрытый откат на оставшийся старый.

19 тестов проверяют настоящие Universal-подписи, каждую архитектуру (в том числе
ослабленный/чужой Intel-срез на Apple Silicon), изменение подписанного кода,
хеши, метаданные, thin/неверные заголовки, права/ACL/ссылки, повторы и устаревшие
операции, прерывание после сохранения кандидата и до/после записи выбора.

остатки аварий сохраняются; ограниченная очистка ещё не реализована.

**Граница результата:** согласована пара на диске, а не работающий процесс.
Ещё нужны контроллер жизненного цикла, освобождение прежних ресурсов,
аутентифицированная проверка запуска кандидата, порядок переключения и
восстановление после ошибки запуска без потери защиты от отката. Установочные
пакеты и приложение не подключены к новым методам. Root-установка, физический
сбой питания, выполнение на Intel/macOS 11 и реальный VPN не проверялись.
Этап 1.5b целиком остаётся открытым.

Итог регрессии: **132 теста за 115 секунд — 131 успешно, 1 пропущен**

с версией протокола, номером релиза и случайным одноразовым значением; принимает
только точное подтверждение. Дескриптор закрывается на всех путях. Фрагменты не
продлевают общий монотонный таймаут обмена. Системные вызовы Security синхронные:
таймаут не прерывает зависший системный вызов, поэтому UI-поток использовать нельзя.

12 тестов используют отдельные подписанные процессы и временные локальные сокеты.
Проверены неверные подпись/идентификатор/защита процесса, подмена номера/протокола/
одноразового значения, частичный ответ, зависание и закрытие дескриптора. Замена
root UID на текущего пользователя доступна только через тестовый compile flag.
Обычная сборка отдельно отвергает даже правильно подписанный непривилегированный
сервер. Положительная проверка настоящей root-службы остаётся в живой приёмке.

`VPNActivationCoordinator` соединяет подготовку, остановку, выбор и проверку
запуска. Невалидная сборка не останавливает прежнюю службу. Подготовленный файл
перепроверяется после остановки, перед атомарным выбором. Ошибка остановки
запрещает выбор/запуск; ошибка или неопределённый исход записи запрещает угадывать
выбранную версию. После запуска проверяется ответ и повторно — выбор на диске.
При ошибке запуска/готовности выполняется остановка возможного процесса;
неподтверждённая очистка возвращается как отдельный признак ошибки.

Восстановление — одна явная попытка остановить управляемую службу, перечитать
проверенное состояние и запустить выбранную версию. До commit остаётся старая
версия, после него нельзя молча откатывать принятую границу безопасности.
Для исправления плохой новой сборки нужен совместимый подписанный релиз с большим
номером; интерфейс авторизованного восстановления ещё не реализован. Нет
автоповторов, сброса повреждённого состояния или ложного «VPN подключён».

18 тестов координатора используют защищённое временное хранилище, настоящие
подписи Universal и запуск инертного тестового сервера. Проверены порядок действий,
ошибки остановки/запуска/ответа/очистки, подмена подготовленного файла, устаревшая
операция, смена выбора при запуске, повторный вход, одинаковое обновление и
прерывания процесса до/после commit с восстановлением отдельным новым процессом.
Запускаемые тестовые серверы не имеют root-прав, не знают профиль и не меняют сеть.

**Оставшаяся граница:** адаптер запуска пока только тестовый. Нужны эксклюзивное
межпроцессное владение службой, настоящий launchd-адаптер с подтверждённой очисткой,
безопасный транспорт и production-ответ готовности по фактическому состоянию,
отмена/приоритет ручного выключения, ограничение повторных запусков и интеграция
установки/updater. Локальная блокировка экземпляра координатора не является
межпроцессной защитой. Успешный ответ подтверждает готовность процесса в момент
проверки, а не работу VPN. Этап 1.5b целиком не закрыт.

Итог полного прогона: **162 теста за 130 секунд — 161 успешно, 1 пропущен**
(opt-in установка Sparkle в одноразовое приложение). Все 30 новых тестов проходят:
12 для проверки готовности и 18 для активации. Обычные и тестовые компоненты
собраны для arm64/x86_64 с минимальной macOS 11; исполнение проверено только на
текущем Mac с Apple Silicon. Реальная служба не установлена, системные настройки
и профиль не затронуты, приватные релизные ключи не использовались. Пуш и релиз
не выполнялись. Следующий блок: эксклюзивное владение жизненным циклом между
процессами и безопасный production-транспорт/адаптер службы, затем интеграция
установки и обновлений. Доработки фиксируются двумя смысловыми коммитами.

### Продолжение 1.5b — межпроцессное владение жизненным циклом

Из перечисленного выше закрыт первый пункт: экземплярная блокировка координатора
заменена настоящей межпроцессной. `VPNLifecycleOwnership` открывает `lifecycle.lock`
относительно защищённого дескриптора каталога, требует приватный каталог 0700 и
файл 0600 с одной ссылкой, нужным владельцем и без ACL, затем берёт эксклюзивный
неблокирующий `flock`. Ядро освобождает такую блокировку при завершении процесса,
включая аварийное: погибший супервизор не оставляет службу неуправляемой.

Удерживаемый дескриптор сам по себе не является владением. `check()` заново
проверяет права файла и доказывает, что каталог по-прежнему указывает именно на
удерживаемый inode. Переименование, подмена и удаление замка распознаются и
приводят к отказу: иначе второй супервизор возьмёт блокировку на новом файле и
начнёт управлять той же службой. Координатор перепроверяет аренду перед
остановкой, перед фиксацией, перед запуском и перед возвратом готовности.

При потере аренды после запуска ошибка возвращается **без** остановки и очистки:
останов в этот момент мог бы выключить службу, которой уже управляет новый
владелец. Аренда не является ни разрешением запускать релиз, ни доказательством
работы службы, ни заменой дисковой блокировки хранилища.

14 тестов владения запускают отдельные настоящие процессы в одноразовых каталогах:
отказ второму процессу, освобождение после принудительного завершения владельца без
какой-либо очистки, отказ второй аренде внутри того же процесса, обнаружение
переименования/удаления/освобождения, отказ на симлинке, групповых правах, жёсткой
ссылке, ACL файла и каталога и на общем каталоге. Ещё 4 теста активации проверяют
занятое другим процессом владение и потерю аренды до остановки, после остановки и
после запуска. Мутационные проверки подтвердили, что снятие `flock` или сверки
inode роняет соответствующие тесты.

Итог полного прогона: **180 тестов за 131 секунду — 179 успешно, 1 пропущен**
(opt-in установка Sparkle в одноразовое приложение). Обе архитектуры собираются с
минимальной macOS 11, координатор компилируется и без тестовых флагов. Исполнение
проверено только на текущем Mac с Apple Silicon.

**Оставшаяся граница:** взаимное исключение доказано между непривилегированными
процессами; root-служба и launchd в этом не участвовали. Дальше нужны настоящий
launchd-адаптер с подтверждённой очисткой, безопасный транспорт и production-ответ
готовности по фактическому состоянию, отмена/приоритет ручного выключения,
ограничение повторных запусков и интеграция установки/updater.

### Продолжение 1.5b — адаптер службы launchd

Тестовый адаптер запуска заменён рабочим: `VPNLaunchdRuntime` реализует контракт
`VPNActivationRuntime` поверх настоящего launchd. Домен, метка, путь описания
службы, имя сокета и вектор аргументов зафиксированы в коде; ни путь, ни PID, ни
команда не приходят извне. Исполняемым файлом становится только контентно-
адресованный файл, уже проверенный хранилищем для этого развёртывания, и адаптер
перепроверяет его как приватный обычный файл с одной ссылкой перед тем, как
передать путь launchd. Производственный вход требует root и системного домена;
узкий тестовый шов добавляет конструктор для пользовательского домена и
отсутствует в обычной сборке.

Остановка не считается выполненной по коду возврата. После `bootout` адаптер
подтверждает: launchd больше не знает метку, на сокет никто не отвечает, и
оставшаяся конечная точка удаляется — только если это действительно наш сокет, а
не подменённый файл или ссылка. Неподтверждённая остановка — ошибка, поэтому
координатор не может запустить второй экземпляр поверх живого. Запуск отказывает,
пока сокет существует, пишет описание службы атомарно (0644, приватный временный
файл, fsync, переименование, fsync каталога), выполняет `bootstrap` и ждёт
конечную точку до дедлайна вызывающего. Каждый вызов `launchctl` — прямой запуск
без оболочки и без наследуемого окружения, с принудительным завершением по
дедлайну.

11 тестов гоняют настоящий адаптер через настоящий координатор и настоящий
launchd в GUI-домене текущего пользователя под одноразовой меткой (не в системном
домене и не в `/Library/LaunchDaemons`), выгружая метку после каждого теста.
Проверены: запуск службы с аутентификацией готовности, остановка с подтверждением
исчезновения метки и процесса helper по PID, удаление сокета, идемпотентная
остановка, замена работающей службы новым процессом при повторном обновлении,
восстановление выбранного релиза, служба, которая никогда не слушает (отказ внутри
дедлайна и выгрузка), посторонний файл на имени сокета (активация останавливается),
приватная атомарная запись описания и отказ производственного входа без root.
Мутационная проверка подтвердила, что отказ от удаления сокета роняет три теста.

Итог полного прогона: **191 тест за 161 секунду — 190 успешно, 1 пропущен**
(opt-in установка Sparkle). Обе архитектуры собираются с минимальной macOS 11,
адаптер компилируется и без тестового шва.

**Оставшаяся граница:** запущенная фикстура инертна — она открывает сокет,
отвечает на запрос готовности и больше ничего не делает. Доказана механика
активации, а не установка root-службы: системный домен, авторизация установки,
права сокета, создаваемого настоящим helper, политика перезапуска (KeepAlive),
приоритет ручного выключения и ограничение повторных запусков остаются открытыми.
Самого production-helper, отвечающего на запросы, ещё нет.

### Продолжение 1.5b — серверная сторона и ответ по фактическому состоянию

Появился недостающий конец канала: `VPNHelperListener` внутри helper. Это не
диспетчер команд — единственное доступное поведение — ответить на один
фиксированный 56-байтный запрос 56 байтами. Ни путь, ни аргумент, ни профиль, ни
операция, ни таймаут не задаются вызывающим. Каждое соединение сначала
аутентифицируется клиентской политикой из подписанного релиза: UID владельца и
запиненные хэши подписи приложения, с повторной проверкой прямо перед ответом.
Отказ стоит только этого соединения — listener продолжает обслуживать, поэтому
отвергнутый, молчащий или испорченный клиент не может лишить обслуживания
настоящего.

Конечная точка создаётся внутри уже защищённого каталога, путь берётся из
проверенного дескриптора, bind выполняется под umask 0177, после чего listener
убеждается, что получился именно сокет 0600 нужного владельца. Существующий сокет
никогда не удаляется: он означает, что супервизор не подтвердил прошлую остановку,
и тихий перехват скрыл бы это. Ответ привязан к релизу: запрос с другой версией
протокола или другим номером отвергается, а квитанция отправляется только если
собственное состояние готовности helper в этот момент говорит «да». Просто
работающий процесс не может ответить за неготовый helper.

10 тестов запускают production-listener и клиентский probe как отдельные
подписанные процессы: аутентифицированный клиент получает квитанцию, несколько
клиентов подряд обслуживаются, чужая подпись отвергается, клиент вне пинов релиза
отвергается, неготовый helper не отвечает, запрос про другой релиз отвергается,
конечная точка приватна, существующая точка не перехватывается, общий каталог
отвергается, молчащий клиент не блокирует следующего. Мутационная проверка
подтвердила, что снятие проверки состояния или привязки к релизу роняет
соответствующие тесты.

Набор launchd-тестов переведён на этот же listener: 11 тестов теперь проверяют
настоящую серверную сторону, настоящий адаптер и взаимную аутентификацию — драйвер
выступает приложением владельца и должен пройти проверку по пинам релиза.

Итог полного прогона: **201 тест за 175 секунд — 200 успешно, 1 пропущен**
(opt-in установка Sparkle).

**Оставшаяся граница:** привилегированных операций по-прежнему нет — диспетчеризация
типизированных запросов, лимиты кадров и повторная валидация профиля в службе
появятся только вместе с самими операциями. Всё проверено между
непривилегированными процессами: системный домен, авторизация установки, политика
перезапуска, приоритет ручного выключения и ограничение повторных запусков
остаются открытыми.

### Продолжение 1.5b — ручное выключение и бюджет попыток

`VPNActivationBudget` отвечает на один вопрос — можно ли ещё раз попытаться
запустить helper — из durable-состояния рядом с политикой релиза. Два правила:
решение владельца выключить VPN старше любой автоматической попытки, а
повторяющиеся неудачи прекращают автоматические перезапуски вместо бесконечного
цикла. Сам по себе бюджет ничего не разрешает: он не запускает, не останавливает
и не выбирает релиз, и он не является состоянием VPN.

Попытка списывается **до** её выполнения, поэтому процесс, умерший посередине,
всё равно её потратил, и цикл падений не может перезапускать службу вечно. Счётчик
обнуляет только подтверждённая активация, и та же запись фиксирует, что VPN должен
быть включён. Явное действие пользователя проходит всегда: бюджет ограничивает
автоматику, а не владельца. `turnOff` сначала фиксирует решение, затем
останавливает — неудачная или прерванная остановка не отменяется автоматикой.
Отсутствующая запись — первый запуск; повреждённая отвергается, а не «чинится» в
чистый бюджет. Координатор списывает попытку только когда запрос дошёл до запуска
службы: неверная подпись или устаревшая ревизия не тратят попытку.

10 тестов активации: чистый бюджет после успеха, неверный запрос ничего не тратит,
автоматика останавливается после трёх неудач, явная попытка проходит при
исчерпанном бюджете и обнуляет его, аварийно завершённая попытка всё равно
списана, ручное выключение старше автоматики, владелец включает VPN обратно,
ручное выключение сохраняется при неудачной остановке, повреждённая и
доступная группе записи отвергаются. Мутации подтвердили: снятие любого из двух
правил или списание после попытки роняет эти тесты.

Итог полного прогона: **211 тестов за 168 секунд — 210 успешно, 1 пропущен**.

**Оставшаяся граница:** остаётся последний пункт 1.5b — интеграция установки и
обновления: bootstrap доверенного ключа при первой установке, авторизация
установки root-службы в системном домене, транспорт команд и связка с updater.
Автоматического запуска при загрузке и приёмки на чистой системе пока нет.

### Продолжение 1.5b — авторизованная установочная последовательность

`VPNInstaller` — единственное место, где компоненты собираются вместе, в
фиксированном порядке: подготовка защищённого каталога → аренда жизненного цикла →
проверка подписанного релиза → публикация транзакции «политика + бинарник» →
активация через launchd. Аренда берётся первой: установка не должна гоняться с
работающим супервизором за остановку и запуск службы. Это не точка входа для IPC,
не updater и не пользовательская команда — вызывающий обязан уже иметь системную
авторизацию установки, а доверенный ключ релиза должен быть вшит в код, а не
прочитан из хранилища или сети.

`install` отказывает, если политика уже существует: существующая установка
меняется через `update`, а не переустанавливается поверх. `update` никогда не
создаёт каталог, поэтому отсутствующий отвечает «не установлено», а небезопасный
по-прежнему виден как небезопасный и молча не переподготавливается. Ошибки
хранилища остаются собой: повреждённая установка не выдаётся за отсутствующую и
не «чинится» обновлением. Оба производственных входа требуют root.

8 тестов прогоняют всю последовательность без привилегий: одноразовый базовый
каталог вместо `/Library/Application Support` и пользовательский домен launchd
вместо системного. Проверено: установка создаёт каталоги 0700, публикует политику
и запускает службу, отвечающую на запрос готовности; повторная установка
отвергается и не трогает работающую службу; неподписанный релиз ничего не
устанавливает и не запускает; обновление заменяет установленный релиз; обновление
без установки отвергается; удерживаемая аренда блокирует параллельную установку;
общий каталог приложения отвергается; производственный вход отказывает без root.

Итог полного прогона: **219 тестов за 188 секунд — 218 успешно, 1 пропущен**.

**Оставшаяся граница:** ни один шаг не выполнялся от root и в системном домене.
Не реализованы вшитый доверенный ключ и его смена, удаление службы,
восстановление при загрузке и связка с updater. Привилегированных операций и
самого VPN по-прежнему нет.

### Продолжение 1.5b — удаление службы и поведение при загрузке

Удаление устроено зеркально установке и решает, что можно удалять, **до** того как
что-либо останавливает: посторонний файл прерывает удаление, а не оставляет
остановленную службу и наполовину снесённую установку. Затем служба
останавливается с подтверждением, снимается описание launchd и удаляются только
имена, которые создаёт этот компонент — точные имена или контентно-адресованный
шаблон helper. Замок жизненного цикла удаляется последним: именно в этот момент
заканчивается исключительное владение. Каталоги приложения удаляются, только если
уже пусты и по-прежнему проходят проверки; ничего рекурсивного и принудительного.

Пока описание службы существует, launchd запускает helper при каждой загрузке, не
спрашивая координатор. Так helper возвращается после перезагрузки — и поэтому
удаление обязано снять описание. Тесты закрывают обе ветки: после остановки
описание остаётся и его загрузка снова поднимает службу; после удаления загружать
нечего.

6 новых тестов: полное удаление (служба выгружена, описание и каталоги исчезли),
удаление без установки, посторонний файл прерывает удаление и служба продолжает
работать, удерживаемая аренда блокирует удаление, и две ветки перезагрузки.
Мутации подтвердили: удаление «всего подряд» и оставленное описание launchd роняют
соответствующие тесты.

Итог полного прогона: **225 тестов за 191 секунду — 224 успешно, 1 пропущен**.

**Оставшаяся граница:** осталось вшить доверенный ключ релиза и его смену и
связать всё с updater. Ни один шаг по-прежнему не выполнялся от root и в системном
домене; привилегированных операций и самого VPN нет.

### Начало 1.5c — типизированный протокол запросов

`VPNHelperProtocol` — весь словарь, который понимает привилегированная служба:
фиксированные кадры, фиксированные размеры, никаких строк, путей и оболочки.
Запрос — это magic, 16-битный код операции, 64-битная ревизия релиза, с которым
клиент считает, что говорит, и полезная нагрузка с длиной. Ответ — magic, статус
и нагрузка. Добавление операции — осознанное изменение в этом файле, а не то, что
может запросить клиент или подразумевать полезная нагрузка. Сейчас в списке ровно
одна операция — `status`, отвечающая номером и версией протокола работающего
релиза.

Лимиты — часть формата: не более 64 КиБ на нагрузку, не более восьми запросов на
соединение, дедлайн на каждый запрос (повторная аутентификация пира стоит
реального времени) и отдельный предел на всю беседу, чтобы медленный клиент не
удерживал однопоточную службу на сумму всех дедлайнов. Слишком большой или
испорченный кадр обрывает соединение на заголовке, без чтения тела. Запрос с
другой ревизией отвергается, а не исполняется: служба, заменённая посреди беседы,
не выполнит операцию, предназначенную другой сборке. Обе стороны заново
аутентифицируют друг друга вокруг каждого запроса. Исчерпав бюджет, служба ждёт,
пока пир закроется сам, а не рвёт соединение поверх своего последнего ответа.

`VPNHelperSession` — клиентская сторона: рукопожатие готовности, затем тот же
ограниченный бюджет на том же соединении, и закрытие при любом отказе или ошибке
транспорта вместо повторов на соединении, чью идентичность не удалось подтвердить.
Обе стороны используют одну реализацию кадрирования с дедлайнами.

9 тестов гоняют протокол против настоящего listener: `status` отвечает работающим
релизом, несколько запросов делят одно аутентифицированное соединение, бюджет
клиента исчерпывается после восьми, служба перестаёт отвечать после своего
бюджета, неизвестная операция отвергается, запрос про другую ревизию отвергается,
лишняя нагрузка отвергается, слишком большой кадр обрывает соединение быстро, а не
по дедлайну, испорченный кадр — тоже. Мутации подтвердили, что снятие лимита
длины или привязки к ревизии роняет соответствующие тесты.

Итог полного прогона: **234 теста за 201 секунду — 233 успешно, 1 пропущен**.

**Оставшаяся граница:** привилегированных операций нет — `status` ничего не читает
и ничего не меняет. Приём профиля с повторной валидацией в службе, атомарное
применение и восстановление после ошибки — следующий шаг 1.5c.

### Продолжение 1.5c — первая ограниченная операция

`storeProfile` — первая операция, которая что-то меняет. Служба не доверяет
импорту клиента: она заново разбирает байты **тем же импортёром, что и
приложение**, и сохраняет только нормализованный, ужесточённый результат в
`profile.ovpn` (0600) внутри защищённого каталога. `VPNProfileVault` пишет
атомарно — временный файл, fsync, переименование, fsync — поэтому отказ или
прерванная запись оставляют прежний профиль ровно таким, каким он был, и никогда
не оставляют обрезанный. Профиль больше лимита кадра вообще не уходит от клиента.
Сохранение профиля по-прежнему ничего не подключает: ни маршрутов, ни DNS, ни
OpenVPN.

5 тестов: валидный профиль перепроверяется и сохраняется в нормализованном виде,
служба отвергает то, что отвергает её собственный импортёр (даже если клиент это
принял), отвергнутый профиль не трогает сохранённый, пустая нагрузка отвергается,
слишком большой профиль не отправляется. Мутация «хранить байты клиента без
проверки» роняет три теста.

Итог полного прогона: **239 тестов за 210 секунд — 238 успешно, 1 пропущен**.

**Оставшаяся граница:** дальнейшие операции появятся вместе с туннелем —
применение профиля, маршруты, DNS и восстановление после ошибки применения. Ни
одна привилегированная операция всё ещё не выполнялась от root.

### Этап 2 — безопасная миграция старых маршрутов

`VPNLegacyMigration` переносит `VPN_ROUTES` из конфига CLI в новый список
ресурсов. Это односторонний перенос только на чтение: старый файл не изменяется,
оболочка не вызывается, ни одно значение из файла не исполняется и не
раскрывается, а сама миграция не включает VPN и не выдумывает профиль.

Значение читается так, как его прочитала бы оболочка: учитывается последнее
присваивание `VPN_ROUTES=` (закомментированные строки игнорируются),
поддерживаются кавычки, `export` и завершение значения на комментарии. Всё, что
умел старый CLI, — это IPv4-хосты и сети, поэтому домены, IPv6, мусор и подстановки
команд просто пропускаются и считаются в счётчике пропущенных. Маршрут по
умолчанию и префиксы короче /8 не мигрируют: первая версия не переносит правило
«весь интернет в туннель». Дубликаты схлопываются, ресурсы переносятся без
выдуманных имён, а список с уже добавленными ресурсами никогда не перезаписывается
— миграция один раз заполняет пустой список.

Проверки добавлены в набор ядра отдельной группой: порядок и формат значений,
последнее присваивание, комментарии, пустое/отсутствующее значение, смешанный
список с подсчётом пропущенных, заполнение пустой конфигурации, отказ второй
миграции и то, что после миграции VPN остаётся выключенным и без профиля.
Мутации подтвердили, что снятие проверки ширины префикса или запрета перезаписи
роняет тесты.

Итог полного прогона: **240 тестов за 230 секунд — 239 успешно, 1 пропущен**.

**Оставшаяся граница:** миграция не вызывается из интерфейса — новый экран VPN ещё
не построен, и это часть этапа 6. Универсальная криптографическая проверка
профиля по-прежнему не встроена.

### Завершение 1.5b — доверенный ключ релиза в Keychain

`VPNReleaseTrust` — единственное место, где helper и установщик узнают, кому
доверять, и ключ вшит в код намеренно: чтение его из хранилища, настроек или сети
позволило бы тому, кто контролирует источник, авторизовать root-код. В репозитории
лежит только публичная половина (`app/vpn-release-public-key.txt`, продублированная
константой). Пустая константа отказывает: сборка без доверенного ключа не
авторизует ничего — это проверяется отдельной компиляцией в тесте.

`app/vpn-release-key.swift` хранит приватный ключ так же, как хранится ключ
Sparkle: в Keychain, никогда на диске, никогда в argv и никогда в выводе.
`generate` записывает публичную половину и отказывается перезаписать
существующий ключ без явного `--force`, потому что смена ключа обесценивает все
прежние релизы. `sign` даёт отделённую подпись ровно над теми же байтами с
разделением назначения, которые проверяет helper. `verify` прогоняет собственный
верификатор helper: формат, протокол, номер и запиненные хэши, а не только байты
подписи. Флаг `--keychain` направляет операции в другую связку — так тесты вообще
не касаются рабочей связки разработчика.

9 тестов создают и удаляют одноразовую связку: публичная половина публикуется, а
секрет ни разу не появляется в выводе; изменённое описание релиза не проходит
проверку; чужой ключ не может подписать за этот; существующий ключ не заменяется
молча, но смена остаётся возможной; подпись без ключа отвергается; вшитая
константа совпадает с опубликованным файлом; сборка без доверия отказывается
строить authority.

**Ключ выпуска создан 7 сентября 2026** в login-связке владельца
(`kz.documentolog.proxypilot.vpn-release`). Приватная половина не покидала
Keychain и в этой сессии не отображалась; цикл «подписать → проверить» на
настоящем ключе выполнен на одноразовом описании релиза.

Итог полного прогона: **249 тестов за 211 секунд — 248 успешно, 1 пропущен**.

**Оставшаяся граница:** смена ключа — это выпуск новой сборки с новой константой;
цепочечной ротации (новый ключ, подписанный старым) нет и она требует отдельного
согласования. Связка с updater не сделана. Ни одна подпись ещё не авторизовала
настоящую root-установку.

### Продолжение 1.5b — отдельный updater в проверочной сборке, 8 сентября

Добавлен opt-in режим `PROXYPILOT_ISOLATED_UPDATER=1` в `app/build.sh`:
основной app-бинарник собирается без Sparkle и подписывается `runtime,hard,kill`;
Sparkle находится только в отдельном непривилегированном nested-приложении.
Обычная сборка и release pipeline не переключены. Кандидат собирался в новый
временный каталог, не заменял и не запускал установленный ProxyPilot.

`app/update-worker/` содержит модель для существующих настроек, ограниченный
канал и worker. Проверяется точный вложенный путь и подпись перед запуском;
не передаются произвольные аргументы, пути или окружение. Обновляется родительское
приложение: и версия, и настройки Sparkle относятся к нему. У worker нет VPN
операций; его сообщения не являются разрешением для привилегированной службы.

Подтверждены 24 новые проверки: 11 для транспорта и 13 для модели/worker.
Настоящий Sparkle принимает подписанный feed, показывает callback результата
ручной проверки для актуальной/новой версии и ошибки сети, отвергает изменённый
feed. Автопроверка сохраняется в настройках родительского приложения и переживает
перезапуск. Превью не запускает worker; сбой даёт повторную попытку. Имитация
подготовки к установке проверяет однократное завершение, отмену, поздний callback
и неожиданный/повторный запрос. Транспорт проверен на фрагментации, размерах,
неверном направлении, обрыве, SIGPIPE, таймауте и зависшем получателе.

### Продолжение 1.5b — идентичность установщика до замены службы, 8 сентября

Найден разрыв в порядке действий: подпись кандидата проверялась до его активации,
но сам установщик обнаруживал несовпадение с новыми app-pins только на последующей
проверке готовности службы. К тому моменту новая политика уже могла быть выбрана,
а рабочая служба — заменена и затем остановлена после ошибки.

В `VPNInstaller.install/update` перед созданием/открытием установки добавлена
проверка подписанного VPN-релиза и живого текущего процесса. Используется
`SecCodeCopySelf`, real/effective UID, точный идентификатор приложения и CDHash,
`runtime,hard,kill`, действующий статус без отладки и исключений entitlements.
Общая реализация с проверкой IPC-процесса исключает более слабый вариант для
установщика. Путь к приложению, номер версии, данные updater и произвольный PID
не являются источником идентичности.

Это только предварительная проверка кандидата/процесса, не новое разрешение на
установку. Проверка `previous: nil` здесь не сбрасывает принятую ревизию: хранилище
снова проверяет подпись, владельца, expectedSequence и запрет отката под блокировкой.
После запуска службы сохранена взаимная аутентификация. В updater не добавлены
команды выдачи прав, установки root-службы или автоматического принятия новых pins.

Проверено без root:

- разрешённая собственная сборка проходит, другой hash/identifier/UID — нет;
- даже явно подписанные pins не позволяют исключения hardening/entitlements;
- производственная installer-role не принимает обычный UID;
- неразрешённый установщик не создаёт каталог установки;
- старый app не меняет PID, файлы политики/бюджета и выбранный helper при попытке
  установить релиз с pins новой сборки;
- процесс с идентификатором updater отвергается даже при совпадающих подписанных
  pins и более строгом hardening, чем у настоящего worker;
- отдельно разрешённая новая сборка обновляет тестовую службу, старая после этого
  не может продолжить замену; неверная ожидаемая ревизия отвергается и у новой.

Целевые наборы: **20 проверок идентичности за 7,706 с и 19 установочных проверок
за 32,810 с — все 39 прошли**. Новых тестов 10, остальное — существующая регрессия.
Тестовый режим меняет только root-policy на policy текущего пользователя; exact
app-подпись проверяется по-настоящему. Службы работают в уникальных GUI-метках
launchd и удаляются после проверки. Production-вариант собран без test-seams для
обеих архитектур/macOS 11, но не исполнялся с root. Выпускной ключ/Keychain,
настоящий VPN-профиль, установленный app и системные прокси не использовались.

Финальная общая регрессия с включёнными обоими opt-in наборами обновления:
**310 тестов за 367,193 с; 309 успешно, 1 пропущен**, без ошибок. Пропущен прежний
отдельный тест установки Sparkle; 9 тестов `test_vpn_release_key` намеренно
исключены, чтобы не использовать Keychain. Ручная native-приёмка не повторялась.

Осталось связать фиксированный установочный вход с отдельным системным согласием
и доставкой подписанных материалов, затем провести root ↔ user приёмку. Успешное
обновление через Sparkle само по себе не даёт новой сборке доступа к старой службе.
Будущая интеграция должна завершать управляемый VPN перед заменой app с потерей
совместимости и сохранять желаемое состояние; отмена не должна оставлять активный
туннель, которым новое приложение не может управлять. Эти операции ещё не
реализованы; нынешний proxy-мост и простой UI не изменены. Пуша/релиза нет.

### Продолжение 1.5b — рабочий процесс службы и восстановление запуска, 8 сентября

Добавлен отдельный Universal/macOS 11 `vpn-helper` с фиксированным root-входом.
При запуске он заново проверяет подписанный выбранный релиз и собственный процесс,
открывает только штатные защищённые каталоги и запускает аутентифицированный idle-
listener. Профиль, туннель, маршруты и DNS при этом не применяются.

Владение работающим процессом отделено от короткой установочной транзакции:
`runtime.lock` удерживается всю жизнь службы, `lifecycle.lock` — координатором
замены или начальным запуском. Второй процесс не отбирает сокет у первого. После
краха удаляется только принадлежащий службе сокет с явным `ECONNREFUSED`; файл,
ссылка, живой listener и неопределённая ошибка остаются нетронутыми. При запуске
без координатора учитываются сохранённое ручное выключение и бюджет попыток.

Первый прогон обнаружил конкуренцию проверки готовности и финального чтения
установщиком: повторное открытие политики брало её writer-lock. После начальной
криптографической проверки служба теперь следит за идентичностью защищённой
атомарной записи без захвата этого замка; изменение выбора завершает процесс.
Также устранено потенциальное двойное закрытие дескрипторов при отказе выдачи
аренды. Удаление знает точное новое имя runtime-lock.

Повторная проверка: **26 из 26 сценариев службы за 46,545 с**, включая 19 прежних
установочных сценариев уже с новым процессом, восстановление после краха,
отказ второму экземпляру, ручное выключение, исчерпанный бюджет и чужой endpoint.
Отдельно **14 из 14 проверок lifecycle за 2,895 с**. Production helper собран и
проверен для обеих архитектур, но эти тесты выполнялись в пользовательском
launchd-домене. Root-приёмку и реальное подключение VPN это не подтверждает.

ранее известными файлами компонента. Инструкция: `app/vpn-package/README.md`.

### Системная приёмка 1.5b — первый запуск и исправление cross-UID, 8 сентября

После разрешения Keychain существующий ключ подписал sequence 1; отдельная

Системная отмена разрешения в этом запуске не проверялась.

Первая пользовательская команда status отказала. Read-only диагностический
инструмент подтвердил: сокет доступен, peer UID = root, audit token получен,
но стандартный `SecCodeCopyGuestWithAttributes` возвращает **100013**.
В исходниках [Apple Security errors.cpp](https://raw.githubusercontent.com/apple-oss-distributions/Security/main/OSX/libsecurity_utilities/lib/errors.cpp)
это Unix errno 13 (`EACCES`) с базой 100000. Стандартный код ищет дисковое
представление процесса, которое пользователь не может прочитать из закрытого
каталога. Root-установщик этого ограничения не замечал.

Для **plain Mach-O helper** добавлен `kSecGuestAttributeDynamicCode`: тот же
kernel audit token получает представление подписи из ядра. По
[Apple cskernel.cpp](https://raw.githubusercontent.com/apple-oss-distributions/Security/main/OSX/libsecurity_codesigning/lib/cskernel.cpp)
оно связано с kernel CDHash/статусом процесса. На установленной root-службе
диагностика получила 0 для получения кода, проверки validity и signing info;
идентификатор совпал. Это ещё не успешная пользовательская команда: неприкреплённый
диагностический инструмент не получает права клиента и ничего не отправляет.

Проверка точных pins, UID, hard/kill/runtime, debugged и отсутствия entitlements
не ослаблена. Для app/installer остаётся прежняя проверка sealed bundle;
никакие PID, пути или Info.plist от собеседника не принимаются. Ошибка получения
kernel-backed представления остаётся отказом. Профили/ключи не стали доступнее.

Автоматически воспроизведён запрет чтения файла живого helper без root: успешный
обмен через kernel identity и сохранение отказа неверным pins/слабому/отлаживаемому
коду. **14 проверок readiness за 10,393 с и 65 проверок identity/installer/daemon
за 103,739 с — все 79 прошли.** Сборка исправленного App и полная регрессия
выполняются отдельно; установленная первая idle-служба ожидает проверенное обновление.

### Доставка движка: сборка и подписанная идентичность — 8 сентября

Закрыты первые три подзадачи 1.6. Две офлайн Universal-сборки OpenVPN 2.7.7 со
статической OpenSSL 3.5.8 из разных каталогов совпали целиком, включая подпись:

Пять криптографических самопроверок прошли в каждой; исходники, рецепт и лицензии
сохранены рядом с бинарником. Это проверка на одном compiler/SDK, не исполнение
на Intel/macOS 11 и не подключение к VPN.

Начата четвёртая подзадача: format 2 связывает релиз с отдельными версиями,
размером, SHA-256 и pins движка. Запрещены откат версий компонентов, подмена,

отвергают. Хранилище и пакет ещё не переведены на комплект «служба + движок».

### Проверка предоставленного профиля — 7 сентября

Профиль проверен локально по прямому разрешению владельца, без подключения к серверу и без копирования ключей в репозиторий, чат, временный файл или хранилище приложения. Идентификаторы, адрес сервера и реальные адреса ресурсов в этой записи не сохраняются.

- OpenVPN TUN/UDP, вход по встроенному клиентскому сертификату. Отдельный логин/пароль и пароль ключа в данном файле не требуются; внешних файлов, скриптов, плагинов и SSO/MFA-директив нет. Подтверждение требований сервера всё равно остаётся частью живой приёмки.
- CA и клиентский сертификат разобраны; цепочка и сроки проверены офлайн для клиентского TLS. Закрытым ключом подписано одноразовое локальное тестовое сообщение, подпись проверена открытым ключом сертификата. Проверка отзыва и доступности сервера не выполнялась.
- Поддержаны `tls-cipher` со строгим списком явных современных наборов, `explicit-exit-notify` с необязательным ограниченным числом повторов и ровно одно Windows-исключение `ignore-unknown-option block-outside-dns`. Последнее удаляется вместе с Windows-настройкой, а не разрешает пропуск неизвестных параметров. Семантика сверена с [OpenVPN 2.6 manual](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html).
- Новый импортёр принимает предоставленный профиль. Найдено 10 безопасно разбираемых предложений IP/сетей; DNS в файле не задан. Предложения сохраняются как метаданные отдельно от выбранного списка, ничего не маршрутизируют и не заменяют существующие ресурсы. Маршруты по умолчанию, правила с нестандартным шлюзом/метрикой и некорректной маской не предлагаются автоматически.
- Добавлен явно запускаемый локальный проверяющий инструмент `tests/check_vpn_profile.swift`: выводит только результат, счётчики и признаки способа входа; не печатает ключи, адреса или содержимое профиля. Тесты используют вымышленные данные, не копию реального файла.

**Следующий обязательный рубеж:** доказать установку и обновление ограниченного привилегированного компонента с бесплатной подписью и macOS 11. Тип корпоративного профиля теперь подтверждён офлайн. Нынешний импортёр всё ещё намеренно консервативен: внешние файлы, цепочки из нескольких PEM, устаревшая криптография, SSO/MFA и нестандартные директивы требуют отдельной проверки; это не обещание совместимости со всеми `.ovpn`. Проверка реальной пары сертификат/ключ в этой сессии не означает, что универсальная криптографическая проверка уже встроена в приложение. Нельзя подключить новый переключатель к старому `vpn install` или выдать сохранённую конфигурацию за работающий туннель.

До публичной функции остаются привилегированный компонент, доставка OpenVPN и лицензий, проверка сертификатов/ключей и входа, туннель/маршруты/DNS, интеграция с мостом, автоматика, миграция и настоящий интерфейс. Пуш и релиз ещё не выполнялись.

## Результат для пользователя

В том же окне ProxyPilot появляется необязательный раздел **VPN**. Одно подключение компании, отдельный переключатель и редактируемый список **«Через VPN»**. VPN можно использовать без настройки SOCKS5/HTTP. До добавления VPN его строка на главном экране скрыта; вход в настройку доступен через шестерёнку.

Первое подключение:

1. Настройки → VPN → перетащить файл подключения `.ovpn` в область добавления или нажать «Выбрать файл», без отдельного вступительного экрана.
2. На одном экране проверить выбранный файл и добавить ресурсы: адрес сайта, IP или сеть; название необязательно.
3. Нажать **«Подключить»**. При необходимости появляется настоящее системное разрешение macOS или запрос данных входа. Прогресс виден в том же окне; после подключения открывается главный экран со статусом.

Отдельных экранов повторного подтверждения, имитации разрешения и финальной кнопки «Понятно» в продукте не будет. Удаление подключения и последнего ресурса, напротив, требует короткого подтверждения последствий.

Файл VPN и список ресурсов — разные сущности. Наличие списка в файле не требуется. Замена файла не стирает список, редактирование VPN не меняет адреса SOCKS5/HTTP.

Если в файле уже есть простые безопасные IP-маршруты, их можно предложить пользователю для списка «Через VPN». Найденное показывается до подключения и допускает редактирование; не применяется скрыто. При замене профиля текущий список не перезаписывается. Отсутствие маршрутов или DNS не мешает сохранить профиль и заполнить их позже.

## Решения после UX-аудита

- Убраны лишние страницы первого подключения и двойное сохранение ресурсов.
- Определение офиса и автоматическое отключение VPN в офисе отложены. В первой версии включённый VPN восстанавливается при наличии интернета; решение выключить его остаётся за пользователем.
- После импорта файл и каждый ресурс сохраняются локально, даже без сети. «Подключить» управляет соединением, а не является скрытой кнопкой сохранения.
- В форме ресурса одно действие **«Добавить»** или **«Сохранить»**; на списке нет повторной кнопки сохранения. «Назад» из несохранённой формы отменяет только её черновик.
- Добавлены независимый сценарий «только VPN», удаление VPN, удаление последнего ресурса с выключением и контекстная диагностика.
- В начало работ перенесена проверка реального типа корпоративного профиля: не откладывать обнаружение несовместимого способа входа до приёмки.

## Границы первой версии

- Один OpenVPN-профиль; переключатель VPN независим от большой кнопки прокси.
- Ресурсы: IP/сети и корпоративные домены. Поддержку доменов нельзя выпускать как простое сохранение строки: нужен отдельный этап DNS и маршрутизации.
- CRUD списка, одно явное сохранение в форме и отмена её черновика; без правил «весь интернет» и автоматического добавления широкой офисной подсети.
- Восстановление после сна и смены сети, понятные ошибки и повтор подключения.
- Без изменения статического IP, DHCP и глобального DNS.
- Без определения офиса, WireGuard, каталога стран, цепочек VPN, управления WARP, глобального kill switch и редактора OpenVPN-директив.
- Начальный набор профилей: TUN, сертификаты без пароля, обычный логин/пароль и
  одноразовый код вместо пароля (`auth-user-pass`). Выбор последних двух делается
  один раз, не угадывается из конфига. SSO, серверные challenge/response, нестандартные
  MFA, смарт-карты, TAP и пользовательские скрипты — не обещать без отдельной реализации
  и приёмки; распознавать и объяснять ограничение при импорте.
- Бесплатное распространение, без обязательного платного аккаунта пользователя. Минимальную версию macOS и модель подписания приложения не менять без отдельного согласования.

## Этап 1. Проверить основу установки и разрешений

Сначала небольшой технический прототип, до полноценной разработки экранов.

- С согласия владельца проверить тип настоящего корпоративного профиля или его обезличенный пример: способ входа, TUN/TAP, сертификаты, внешние файлы и необходимость внутреннего DNS. Если нужный компании способ входа вне согласованного объёма, сначала пересогласовать объём. Приватные ключи не переносить в репозиторий или чат; сама проверка файла не означает разрешения на подключение.
- Оставить отдельный процесс OpenVPN Community 2.x; закрепить проверенную версию и зависимости.
- Подготовить воспроизводимую сборку для Apple Silicon и Intel, проверку контрольных сумм, комплект лицензий и соответствующих исходников. Пользователь не должен устанавливать Homebrew.
- Проверить установку привилегированного компонента, отмену разрешения, повторный запуск, обновление и удаление на чистом Mac с текущей бесплатной подписью.
- Использовать системное подтверждение, не собственную форму пароля администратора. Не обещать заранее точный вид окна или единственный запрос за всё время эксплуатации.
- Привилегированный компонент принимает только ограниченный набор проверенных операций. Никаких произвольных shell-команд, путей для записи или исполняемых файлов из пользовательского конфига.
- Проверить, что обновление приложения не оставляет несовместимую старую службу. Платный сертификат или повышение минимальной macOS не являются скрытой частью этого плана.

OpenVPN распространяется под GPLv2 с оговорёнными исключениями; комплект поставки должен соблюдать лицензии движка и зависимостей. [OpenVPN COPYING](https://github.com/OpenVPN/openvpn/blob/master/COPYING).

Современный `SMAppService` доступен с macOS 13, а приложение сейчас собирается для macOS 11. Поэтому выбор механизма регистрации службы должен учитывать обе версии, а не молча поднять системные требования. [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice).

**Готовность:** чистая установка без терминала, безопасное разрешение операций, остановка и удаление компонента; подтверждённый путь обновления. Если бесплатная схема не проходит эту проверку, сначала пересогласовать её, не строить интерфейс на неподтверждённом обещании.

## Этап 2. Конфигурация и безопасный импорт

Предлагаемые отдельные компоненты: `VPNConfiguration`, `VPNResource`, `VPNProfileImporter`.

- Версионированное хранилище VPN отдельно от прокси: идентификатор профиля, желаемое включение, ресурсы, необязательный корпоративный DNS, сохранённая и применённая версии настроек. Новые сведения об офисной сети в этой версии не собираются.
- У ресурса: стабильный ID, необязательное название, тип и нормализованный адрес. Вычисленные IP доменов хранить отдельно от пользовательского списка.
- Черновик формы → валидация → атомарное локальное сохранение → применение при возможности. Отдельно сообщать «Сохранено», «Ожидает подключения» и «Не удалось применить». Отсутствие интернета не отменяет сохранение.
- Если изменение уже активного подключения не удалось применить, оставить предыдущую рабочую версию, пометить новую как ожидающую применения и предложить «Повторить» либо вернуть прошлые настройки. Не выдавать сохранённую версию за реально работающую.
- Блокировать дубликаты, некорректные сети и маршруты по умолчанию; предупреждать о пересечениях с локальной сетью, VPN-сервером и другими маршрутами. Пустой список разрешён при выключенном VPN. Удаление последнего ресурса подтверждает выключение и отмену автопереподключения; лишь затем сохраняется пустой список.
- Мигрировать существующие `VPN_PROFILE`, `VPN_ROUTES`, `VPN_AUTO` без замены адресов примерами. Перед миграцией — резервная копия и возможность отказаться.
- При уже работающих legacy-службах предложить явный переход: не запускать второй туннель; отключить только прежнюю VPN-автоматику после подтверждения. Настройки статического IP не менять.
- Импортировать профиль как данные, собирать новый конфиг из разрешённых параметров. Запретить вложенные произвольные конфиги, скрипты, плагины и перенаправление файлов/служебных сокетов.
- Проверять ссылки на сертификаты и ключи; недостающие файлы запрашивать явно. Хранить защищённую импортированную копию, чтобы удаление файла из «Загрузок» не ломало VPN. Оригинал пользователя не переписывать и не удалять.
- Перетаскивание и системный выбор файла используют один импортёр и одинаковую полную проверку содержимого. Принимать один `.ovpn`, отклонять папки, пустые файлы и неподдерживаемые форматы. Расширение само по себе не доказывает корректность конфига. Ошибка или отмена выбора не изменяет действующий файл, ресурсы и соединение.
- Ключи — в защищённом хранилище с минимальными правами; пароли — в Keychain по согласию, без паролей в аргументах процессов, логах и отчётах.
- «Удалить VPN» после подтверждения останавливает только наш VPN, удаляет его импортированную копию, ресурсы, принадлежащие ему записи Keychain и сетевые изменения. Прокси, чужие службы и исходные файлы остаются. При неудачной остановке не показывать успешное удаление и не терять данные для очистки.

OpenVPN допускает внешние скрипты и плагины: копирование произвольного `.ovpn` в root-конфиг недостаточно для безопасного импорта. [OpenVPN manual](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html).

**Готовность:** круговой тест сохранения/загрузки, сохранение без сети, безопасная миграция старых настроек, отказ от опасного профиля без сетевых изменений, полное управляемое удаление без затрагивания прокси.

## Этап 3. Управление туннелем и IP-маршруты

- Отдельный `VPNController` и ограниченный интерфейс к службе. Не добавлять долгие VPN-проверки в быстрый `app-state` прокси; использовать отдельный снимок состояния с отметкой времени.
- Состояния: не настроен, выключен, подключается, нужны данные/разрешение, подключён, переподключается, нет интернета, ошибка, конфликт.
- Получать события настоящего OpenVPN-подключения через защищённый локальный management-интерфейс; ограничить владельца и доступ к сокету.
- «Подключён» означает завершённое установление туннеля и применение нужных маршрутов, а не просто наличие процесса.
- Исключить навязанный полный туннель и неразрешённые маршруты как из файла, так и от сервера. Собственными правилами управлять явно, включая IPv6; не отключать IPv6 глобально.
- Добавлять IP и сети только в собственный туннель. Сохранять достижимость самого VPN-сервера по исходному пути.
- Вести журнал созданных маршрутов: при остановке, ошибке и восстановлении удалять только собственные записи. Не перезаписывать изменения другого VPN или пользователя.
- Запросы включения/выключения сериализовать; повторное нажатие не создаёт второй процесс. Выключение отменяет ожидающее переподключение.

OpenVPN предоставляет управление через локальный сокет и управление принятием маршрутов сервера; соответствующие опции не заменяют проверку исходного профиля. [OpenVPN manual](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html).

**Готовность:** IP и подсети идут в нужный туннель; обычный маршрут сохраняется; остановка и сбой очищают только собственные изменения.

## Этап 4. Домены, внутренний DNS и совместимость с мостом

Это отдельный обязательный этап, а не косметическое расширение формы.

- Для сайта хранить доменное имя, не отдельную страницу. Поддомены не добавлять неявно.
- Получать все необходимые адреса A/AAAA, учитывать CNAME, срок действия DNS-ответов и смену сети. Устанавливать маршруты до использования новых ответов клиентами.
- Если рабочее имя известно только корпоративному DNS, использовать DNS из допустимых настроек подключения либо показать условный дополнительный шаг **«DNS компании»**. Если адрес неизвестен — готовый запрос к IT, не угадывание.
- Обеспечить доступ к DNS-серверу через туннель до разрешения внутренних имён. Выборочные DNS-настройки применять только к нужным именам/зонам; не подменять общий DNS macOS.
- Для корпоративных запросов исключить скрытый запасной запрос к публичному DNS. При сбое — конкретная ошибка, а не ложное «сайт не существует».
- Подключить доменные правила к DNS-пути самого локального моста: нынешний общий список внутренних и публичных серверов для этого недостаточен.
- Ресурсы VPN должны обходить внешний HTTP/SOCKS-upstream и достигаться через собственный туннель. Пользовательский список исключений не перезаписывать: вычислять отдельное объединение правил.
- Проверить оба локальных протокола, удалённое разрешение имён в SOCKS5 и приложения без системного прокси.
- Проверить приложения с собственным DNS/DoH и IPv6. Если конкретный путь нельзя обеспечить, явно ограничить поддержку; не заявлять универсальную маршрутизацию любого сайта.

Важная граница: сетевые маршруты работают по IP. Разные сайты могут иметь общие IP, поэтому абсолютно точное обещание «только этот домен, никакие другие» для IP-маршрутизации некорректно. Описывать функцию как доступ к корпоративным ресурсам, не как универсальный фильтр сайтов. Неподдерживаемый IPv6 нельзя молча отправлять мимо VPN.

На macOS выборочные DNS-конфигурации поддерживаются системным резолвером; конкретный механизм и восстановление проверить на поддерживаемых системах. Основание: системная документация `resolver(5)`, прочитанная локально.

**Готовность:** внутренний сайт работает по имени через браузер и мост; смена DNS-адресов не ломает маршрут; отключение VPN не оставляет чужую или устаревшую DNS-конфигурацию.

## Этап 5. Автоматика и жизненный цикл

- Не вызывать старый `net_apply` для новой VPN-функции: там есть изменение IP и DHCP. Отдельный наблюдатель сети, сна и пробуждения.
- VPN выключен → не подключаться автоматически. VPN включён → восстанавливать соединение после временных сбоев с ограниченной частотой повторов.
- Не определять офис и не собирать сведения о нём. Удалить из нового UI обещания «сам подключается вне офиса» и «не нужен в офисе». Одинаковая логика переподключения в любой сети; старую автоматику без принятого управления не трогать.
- WARP и другой VPN не выключать. Проверять реальные пересечения маршрутов/DNS, а не наличие любого `utun`. При конфликте — понятная причина и «Повторить» после действия пользователя.
- Закрытие поповера ничего не отключает. Явный выход из приложения останавливает управляемые этой версией VPN и прокси; следующая сессия учитывает сохранённый выбор. Legacy-службы без принятого управления не трогать.
- При обновлении согласовать версии приложения и службы, завершить текущую операцию, сохранить настройки; после перезапуска восстановить нужное состояние. При неудаче — безопасный откат, без бесконечного цикла авторизации.
- При недоступном Keychain показывать «Нужно подтверждение»; не перебирать сохранённый пароль бесконечно.

**Готовность:** сон, пробуждение, смена сети, перезапуск и обновление не оставляют второй туннель или потерянные настройки; ручное выключение сохраняет приоритет.

## Этап 6. Интерфейс по согласованному макету

Предлагаемые файлы: `app/VPNModel.swift`, `app/VPNViews.swift`, отдельные модели конфигурации и импорта; в `main.swift` — только подключение раздела и жизненного цикла. Переиспользовать `app/Controls.swift`.

- Настройки → VPN; краткий статус VPN на главном экране, без второго большого элемента управления.
- Файл → список «Через VPN» с выбранным файлом → «Подключить». Системное разрешение не дублируется собственным экраном, проверка и ошибки встроены в текущее окно; результат виден на главном экране.
- Большая область drag-and-drop при первом импорте; подсветка и «Отпустите файл здесь» при наведении. После выбора — компактная строка с настоящим именем файла и возможностью перетащить замену. «Выбрать файл» доступна с клавиатуры. При замене ресурсы сохраняются; ошибки показываются рядом с областью, а старый профиль остаётся активным. В интерактивном макете проверяется только имя/расширение и непустой размер, содержимое не читается и никуда не отправляется; полноценный импорт относится к будущей реализации.
- Список с кнопкой «+», форма адреса и необязательного названия, редактирование, удаление и отмена формы. Адреса всегда видны, выбранный файл не спрятан. Одно сохранение в форме; на списке — только управление подключением.
- Блок «Не знаю, что добавить» убран. Примеры формата остаются рядом с полем адреса, без отдельного раскрывающегося раздела в списке.
- Дополнительные поля DNS и входа появляются только по необходимости. Никакой настройки офисной сети в первом сценарии.
- Развязать навигацию от `ProxyModel.configured`: не требовать SOCKS5/HTTP для открытия VPN и его работы. На главном экране большую кнопку явно подписать как управление прокси; если настроен только VPN, не вынуждать проходить настройку прокси.
- В настройках VPN добавить «Удалить VPN». После удаления возвращать в настройки приложения, скрывать VPN на главном экране и сохранять прежнее состояние прокси. Удаление последнего ресурса выключает VPN, но оставляет импортированный файл.
- Отдельные сообщения: неверный файл, недостающий сертификат, отказ macOS, неверные данные входа, истёкший сертификат, ошибка DNS/маршрута, недоступный сервер, конфликт VPN.
- Не путать работоспособность сети и права пользователя на сервис. HTTP 401/403 не означает, что туннель сломан; один молчащий сервер не означает отказ всего VPN.
- При ошибке показывать одно основное действие «Повторить» и раскрываемые «Подробности». В подробностях — диагностика и «Скопировать отчёт» с предварительным просмотром; без паролей, ключей, токенов и персональных путей. Диагностика не сканирует всю корпоративную сеть и ничего автоматически не отправляет.
- Кнопки и строки целиком кликабельны, единые hover/pressed-состояния, клавиатура и VoiceOver.
- Обычные экраны укладываются в компактный поповер без лишнего скролла. Длинный список имеет ограниченную высоту: прокручиваются только ресурсы, а заголовок со счётчиком, «+», выбранный файл и основное действие остаются вне прокрутки. У короткого списка нет пустой области и ненужного скроллбара; полоска прокрутки появляется только при переполнении. Без пагинации и отдельного поиска в первой версии.
- Положение списка сохраняется при переходе в редактор, возврате и фоновом изменении статуса. После сохранения видна изменённая или добавленная строка; после удаления — соседняя. Фокус возвращается к соответствующей строке или «+», клавиатурная навигация раскрывает скрытые строки. Длинные названия и адреса переносятся без горизонтальной прокрутки; строки не сжимаются. В макете есть отдельные примеры с 18 ресурсами при настройке и редактировании.
- Превью полностью изолировано: никакого импорта в настоящее хранилище, системных разрешений, фоновых служб, DNS или изменения прокси.

**Готовность:** весь путь проходится без терминала; каждое состояние понятно без сетевых терминов; сохранённые значения показаны вместо плейсхолдеров.

- VPN без прокси; отсутствие VPN на главном экране до импорта и после удаления; сохранение прокси при очистке VPN; удаление последнего ресурса и отмена удаления.
- Машина состояний, таймауты, авторизация, отмена, повторные нажатия и смена сети во время сохранения.
- Управляемый OpenVPN-сервер и DNS в тестовой среде: выбранные ресурсы через VPN, контрольный обычный ресурс — по исходному маршруту.
- Матрица: VPN on/off × прокси off/direct/SOCKS5/HTTP × локальный клиент HTTP/SOCKS5.
- Восстановление маршрутов/DNS после сбоя, перезапуска и обновления; отсутствие изменений в пользовательском окружении у изолированных тестов.
- Геометрия поповера, длинные адреса и ошибки, светлая/тёмная темы, хитбоксы, клавиатура и VoiceOver.
- Полный прогон существующих тестов прокси и Sparkle.

### Живая приёмка перед релизом

Нужны разрешённый тестовый профиль, тип которого проверен уже на первом этапе, список реальных ресурсов и, если используется, DNS компании. Проверка сети пользователя — только в согласованное время; приватный ключ не копировать в чат, репозиторий или отчёт.

Проверить чистую установку перетаскиванием из DMG, обновление с 1.5.1, VPN без прокси, включение/выключение, сон, смену сетей, WARP до и после ProxyPilot, сохранение без интернета, отмену системного разрешения, удаление последнего ресурса и удаление VPN.

Не заявлять совместимость с корпоративным VPN или WARP только по mock-тестам. Без живого прогона — тестовая сборка, не завершённая публичная функция.

После приёмки: новая версия и новый тег, английские release notes, signed appcast/ZIP и проверка опубликованных файлов. Опубликованные версии и теги не переписывать. Сам план не является разрешением на пуш или релиз.

## Порядок поставки

1. Проверить нужный тип корпоративного профиля, бесплатную установку и безопасные разрешения.
2. Конфигурация и импорт → работающий туннель для IP/сетей.
3. Домены/DNS и взаимодействие с мостом.
4. Автоматика → настоящий интерфейс по макету.
5. Полная регрессия → согласованная живая приёмка → выпуск.

IP/сети можно использовать как внутренний промежуточный результат. Публичный выпуск согласованного сценария требует этапа доменов: убирать поддержку сайтов из обещанного объёма без отдельного согласования нельзя.

### Продолжение 1.5bb — recoverable route transaction (30 сентября)

Добавлена отдельная `VPNRouteTransaction`, которая не имеет доступа к OpenVPN
hold, DNS или пользовательскому Connected. Внутренняя factory строит route
identity только из проверенного plan и ставит `RTF_PROTO2` как ownership marker.
Fresh install сначала требует отсутствия всех destinations: даже полностью
совпадающий существующий route считается чужим и никогда не присваивается.

Каждая mutation предваряется durable journal checkpoint. Peer bypass ставится
первым, resource routes — в детерминированном порядке; cleanup всегда идёт в
обратном порядке и удаляет peer bypass последним. После crash in-flight install
сверяется с exact kernel identity и транзакция только откатывается — установка
вперёд автоматически не продолжается. Missing owned route безопасно
reconcile-ится; foreign replacement не удаляется, журнал сохраняется и новый
connect блокируется. Retired journal повторно читает exact inode, unlink-ится и
fsync-ится только после пустого ownership ledger.

Journal validation усилена: `applied` обязан быть непрерывным prefix плана,
install operation — ровно следующим route, remove operation — ровно последним
owned route. Пройдены 28 объединённых route tests и universal arm64/x86_64 helper
build/codesign; production coordinator транзакцию ещё не вызывает и реальная
сеть не менялась.

Межпроцессная route authority уже связана с единственной daemon runtime lease:

crash helper. Затем нужна реальная проверка bundled OpenVPN: controlled hold
release остаётся только bootstrap, а не Connected; `--ifconfig-noexec` нельзя
менять до подтверждения, что routes/DNS всё ещё полностью noexec и rollback готов.

### Продолжение 1.5bl — route lifecycle integration (30 сентября)

### Продолжение 1.5bm — held multi-prompt credential coordinator (30 сентября)

Coordinator теперь может удерживать supervised OpenVPN и management socket на
initial hold, когда сам engine выдаёт credential prompt. Challenge создаётся
только из реально наблюдённого exact prompt; его UUID/generation/kind durable
сжигается до создания transient credential и до первой записи в socket. Private
Key и Auth поддерживаются последовательно в любом порядке с новым UUID для
каждого prompt. Code-only OTP проходит обычный Auth prompt; combined static
challenge по-прежнему fail-closed и не угадывается.

Hold release разрешён ровно один раз и только когда обработаны все обязательные
виды credential из validated application. Stale/replay, rejection, transport
ошибка, unexpected prompt/state или timeout обнуляют secret, переводят durable
attempt в failed и проходят route cleanup barrier до остановки процесса.
Пройдены 42 объединённые coordinator/state/transient/exchange проверки,
production installer fixture и universal arm64/x86_64 build со strict codesign.

Listener IPC пока сохраняет старую fail-closed границу и ещё не передаёт secret
в coordinator. Следующий срез убирает pre-issued challenge из `connect`: API
должен возвращать challenge только после real management prompt, передавать
`submitCredential` в parked coordinator и корректно возвращать следующий
challenge либо внутренний bootstrap status. DNS/UI Connected остаются выключены.

### Продолжение 1.5bn — management-driven credential IPC (30 сентября)

Listener больше не выдаёт challenge по предположению из профиля. `connect`
создаёт exact attempt без challenge, запускает coordinator и возвращает
`needsCredential` только после реального management prompt, уже записанного в
durable state. `submitCredential` передаёт response как `inout` в parked
coordinator; результатом становится следующий fresh challenge либо внутренний
`notReady` после bootstrap и route transaction. Wire schema не менялась.

Raw request payload теперь обнуляется через `defer` на всех путях. Cancel
проверяет exact challenge/binding, сначала останавливает owned runtime через
route cleanup barrier и только затем переводит attempt в off. Listener во всех
managed ветках пересчитывает `tunnelStopped` по фактическому process ownership,
поэтому ошибка cleanup не разрешает новый connect поверх живого процесса.

Пройдены 40/40 listener и 16/16 coordinator tests; production helper повторно
собран для arm64/x86_64 и прошёл strict codesign verify. Реальный prompt order
покрыт management fixture coordinator, listener boundary — отдельным parked
runtime seam. DNS и публичный Connected по-прежнему не включены.

Следующий gate нельзя подменять undocumented global DNS mutation: нужен либо
installed acceptance документированного session-scoped backend, либо решение о
Network Extension entitlement/архитектуре. До этого допустим только внутренний
bootstrap+routes status; release/tag не создаётся.

### Продолжение 1.5bo — explicit route-only capability gate (30 сентября)

Текущая бесплатная helper-архитектура теперь явно принимает для запуска только
IP-адреса и CIDR-сети без corporate DNS. Конфигурации с доменными ресурсами или
DNS по-прежнему можно безопасно сохранить и отредактировать, но coordinator
откажет им до открытия профиля и до запуска OpenVPN с отдельной причиной
`splitDNSUnavailable`. Это исключает ложное частичное подключение, утечку DNS и
поздний отказ уже после появления `utun`.

Ограничение временное и не меняет формат сохранённых настроек. Поддержка доменов
будет разблокирована только документированным Apple split-DNS backend через
Network Extension (`NEDNSSettings.matchDomains`) с требуемым entitlement,
provisioning и installed acceptance. Пройдены 66 capability/coordinator/
listener/state проверок. Публичный Connected и release/tag ещё не включены.

### Продолжение 1.5bp — route-proven Connected для IP/CIDR (30 сентября)

Для поддерживаемой route-only конфигурации helper теперь публикует `connected`
только после exact generation binding, OpenVPN CONNECTED/interface evidence,
активации точной pending-конфигурации и успешной install+verify транзакции всех
owned peer/resource routes. Listener отвечает `ok` только если durable snapshot
уже находится в этой фазе; одного процесса или `utun` недостаточно.

Coordinator сохраняет verifier применённых маршрутов и повторяет проверку при
наблюдении за живым соединением. Ошибка переводит попытку в failed и проходит
route cleanup barrier до остановки OpenVPN. После daemon restart даже ранее
записанный `connected` становится failed с новой generation: прежний runtime и
маршруты нельзя считать доказанными. Перед открытием listener новый daemon под
тем же runtime lease обязательно выполняет journal-backed route recovery; если
cleanup нельзя доказать, endpoint не публикуется. Domain/split-DNS конфигурации
сюда не попадают благодаря предыдущему pre-launch gate.

Frontend model получил ту же явную проекцию доступности без попытки угадать
live state: «добавьте файл», «добавьте ресурсы», «выберите способ входа»,
route-only ready либо понятное объяснение, что доменные имена в этой версии ещё
не поддержаны и следует использовать IP/сети. Это готовит UX-контракт для
следующего подключения настоящего helper session к VPN-экрану.

### Продолжение 1.5bq — authenticated frontend helper discovery (30 сентября)

Устранён chicken-and-egg перед live controller: desktop app больше не должен
искать manifest в DMG или ослаблять peer check до имени процесса. Выбранный root
helper при каждом старте атомарно публикует в защищённой public endpoint
директории один read-only `release-receipt.json`: только owner UID и исходные
signed manifest/signature. Секретов, путей и сетевой конфигурации там нет.

Frontend сначала проверяет canonical файл, root ownership/mode и Ed25519
подпись встроенным public key, затем получает из verified release точные helper
CDHashes и sequence для существующего mutual readiness handshake. Старый,
подменённый или повреждённый receipt не авторизует новую пару app/helper.
Daemon публикует receipt до socket endpoint; uninstall удаляет только этот
известный regular root-owned файл и отказывается при неожиданном типе/режиме.

Frontend получил единственный production entry для helper session: встроенный
release public key проверяет receipt, owner UID должен совпасть с текущим
desktop-пользователем, затем открывается fixed system endpoint и существующий
mutual CDHash handshake. Тестовые peer policy и произвольные пути в этот вход не
попали. Полная VPN-installer сборка приложения одновременно выявила и исправила
пропущенный `VPNEngineSupervisor` в frontend source graph; universal app теперь
снова собирается и проходит deep strict codesign.

### Продолжение 1.5br — one-button live controller (30 сентября)

Добавлен frontend owner полного connect/disconnect flow. Одно включение само
атомарно сохраняет enabled intent, повторно импортирует защищённую копию профиля,
вычисляет exact digest, отправляет profile+application в authenticated helper и
публикует `connected` только после обратного чтения route-proven snapshot с той
же спецификацией. Domain/split-DNS intent останавливается до открытия helper.

Сессия удерживается только на время реальных management credential prompts.
Пароль, code-only OTP и последовательные Auth/private-key prompts получают fresh

сначала подтверждается helper, disconnect сначала доказывает cleanup, и только
после этого пользовательский store сохраняет off и снимает applied snapshot.
Покрыты certificate, password/OTP, два последовательных prompt, cancel,
disconnect и unsupported-domain сценарии.

### Продолжение 1.5bs — первый production VPN screen (30 сентября)

VPN vertical slice подключён к настоящей VPN-installer сборке приложения.
Исправлена скрытая ошибка source graph: `VPNModel` и `VPNLiveController` раньше
добавлялись до инициализации массива исходников и затем терялись; теперь обе
архитектуры действительно компилируют модель, controller и новый экран.

Вход находится в существующих «Настройках → VPN», поэтому большая кнопка на
главном экране остаётся только управлением системным прокси. После импорта на
главном экране виден компактный live-статус VPN, причём до ответа helper не
показывается ложное «выключен». Сам VPN-экран содержит один power action,
route-proven состояния, credential prompt и настройки в том же popover.

Первый сценарий принимает один `.ovpn` через picker или drag-and-drop и всегда
использует общий строгий importer. Для certificate-only профиля вход выбирается
автоматически; для `auth-user-pass` пользователь явно выбирает пароль либо

не добавлен, пока нет его runtime adapter.

Ресурсы показываются настоящим списком с `+`, редактированием, удалением и
подтверждением последнего элемента. IP/CIDR-предложения из профиля добавляются

текущего ограничения split DNS. Длинный список имеет отдельный bounded lazy
scroll. Настройки блокируются при активном туннеле, потому что безопасный live
reapply ещё не реализован.

Синхронный helper controller обёрнут одной последовательной фоновой очередью;
popover не блокируется, а UI-состояние публикуется только на main queue.
Явный «Выйти» сначала требует подтверждённо остановить управляемый VPN, затем
выключает прокси; при недоказанной очистке приложение остаётся открытым и
показывает VPN-ошибку.

Проверены 12 model/controller/UI/layout групп, 21 package test (18 success,
3 opt-in skip) и настоящая universal VPN-installer сборка с deep strict
codesign. Это ещё не release gate: отсутствуют Keychain static password,
domain/split DNS, update/sleep lifecycle и native
installed acceptance с реальным корпоративным сервером. Tag/release не создан.

### Продолжение 1.5bu — bounded launch/wake restore (30 сентября)

Сохранённый `desiredEnabled` теперь используется как намерение восстановить VPN
после запуска приложения и `NSWorkspace.didWakeNotification`. На каждое событие
выполняется ровно одна сериализованная попытка: сначала читается настоящий helper
snapshot; уже доказанный connected не перезапускается, unavailable не уходит в
цикл, off подключается, а оборванный failed/credential attempt сначала проходит
подтверждённую cleanup-остановку и только затем начинает fresh attempt.

Certificate-only профиль восстанавливается без лишнего окна. Если живой OpenVPN
реально запросил пароль ключа, пароль VPN или OTP, приложение открывает popover
с VPN-экраном и fresh challenge. Никаких фоновых догадок о секрете и периодических
повторов не добавлено. Наблюдатель wake удаляется при завершении приложения.

Это закрывает только launch/wake edge. Смена сети, bounded backoff при server
outage, controlled update handoff и native sleep/wake acceptance остаются в
release checklist.

### Продолжение 1.5bw — bounded network-change reconnect (30 сентября)

VPN frontend теперь наблюдает системный `NWPathMonitor`. Первый callback только
запоминает physical-path signature, чтобы не дублировать launch restore;
переходы без доступного пути не запускают бессмысленные попытки. Сигнатура
учитывает только Wi-Fi/Ethernet/cellular и status — собственный `utun` и другие
VPN-интерфейсы не могут запустить reconnect loop. После последующей реальной
смены на satisfied physical path выполняется ровно одна операция на общей VPN
queue.

Если VPN выключен пользователем, операция только обновляет live snapshot. Если
сохранено enabled intent, старый tunnel сначала проходит authenticated
disconnect и route cleanup, затем создаётся fresh connect attempt. Password/OTP
prompt переводит пользователя на VPN-экран; секреты не угадываются и повторный
цикл не запускается. Событие, пришедшее во время другой VPN-операции, безопасно
игнорируется существующим busy gate. Monitor отменяется при завершении app.

Это реакция на подтверждённое изменение доступного network path, а не обещание
совместимости с любым VPN. WARP/другие клиенты не выключаются и их настройки не
меняются; реальное coexistence остаётся пунктом installed acceptance.

### Продолжение 1.5cd — complete redacted OpenVPN 2.7 notifications (1 октября)

Installed 130 failure теперь локализован после ответа на credential prompt:
`stage=bootstrap category=management-protocol`. Нет подтверждения отказа
пароля/OTP, connected state и маршрутов. Аудит bundled upstream `manage.c`
выявил ещё три стандартные формы, отсутствовавшие в fixtures: обе пустые

журналирования или connection authority. Server explanation отбрасывается,
а точный известный label остаётся credentialRejected; неизвестные labels и
malformed messages fail closed. Fixtures теперь проверяют токен перед
CONNECTED с пустой UDP transport парой. Parser 5/5, coordinator 17/17,
listener 43/43 прошли.

Добавлены allowlisted parser error categories для state header, shape count,
tunnel address, peer endpoint и optional local endpoint. Ни адреса, ни reason,
ни token не интерполируются в логи. Кандидат 131 собирается. Эти compatibility
bugs подтверждены кодом upstream/fixtures, но точный вариант текущего installed
protocol refusal требует повторной live попытки. Live acceptance ещё pending.

### Продолжение 1.5ce — Darwin default-route replies (1 октября)

Installed 131 прошёл management bootstrap и новое kernel tunnel evidence:
отказ теперь `stage=routes category=unclassified`. После попытки не осталось
engine process или маршрутов к трём выбранным ресурсам; полное подключение
ещё не засчитано. Read-only production PF_ROUTE harness воспроизвёл отказ
без VPN и без сетевых изменений: lookupExact для каждого ресурса возвращал
malformedMessage на обычном default best-route reply.

Причины: Darwin PF_ROUTE использует ROUNDUP32 (4 байта, не размер Swift Int),
а default netmask имеет sa_len=0 и занимает 4 байта. Наш decoder отвергал
такую маску и /0, хотя RTM_GET возвращает best match, а не только exact match.
Codec и peer resolver теперь используют 4-byte alignment. Только RTAX_NETMASK
может иметь нулевую длину. Валидный default RTM_GET возвращает nil exact
snapshot; /0 никогда не становится owned route, mutation evidence или VPN
resource. RTM_ADD/DELETE с default evidence по-прежнему отклоняются.

Независимые IPv4/IPv6 wire fixtures проверяют 4-byte zero mask, default fallback
перед exact install, запрет default delete/mutation и повреждённых sockaddr.
Read-only harness после исправления прошёл peer lookup и все три resource
lookup. Это подтверждает исправление локально воспроизведённого блокера,
но реальная route installation/disconnect acceptance требует кандидата 132.
Route socket 2/2, peer evidence 2/2, transaction 8/8, tunnel route controller
7/7, route plan 15/15, coordinator 17/17, listener 43/43: 94/94 прошли.
Источник ABI: Apple XNU bsd/net/rtsock.c ROUNDUP32:
https://github.com/apple/darwin-xnu/blob/main/bsd/net/rtsock.c
